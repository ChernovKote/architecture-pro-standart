| Код | Требования                         | Комментарий  |
|-----|------------------------------------|--------------|
| F   | Функциональные (Functionality)     |              |
| F1 | На сайте клиент должен видеть доступные депозитные продукты и актуальные ставки, оставить Ф. И. О. и телефон и отправить заявку | Кол-центр получает заявку и связывается с клиентом; менеджер может предложить особые условия. Новый клиент должен прийти в отделение для идентификации |
| F2 | В интернет-банке клиент должен видеть доступные и персональные ставки, выбрать счёт и сумму и отправить заявку на депозит | В MVP заявка обрабатывается бэк-офисом в АБС |
| F3 | Клиент должен получить SMS после подтверждения ставки и после открытия депозита |  |
| F4 | Заявку на кредит можно подать с сайта и из интернет-банка |  |
| F5 | На сайте клиент должен видеть условия кредита из Кредитного конвейера и подать заявку, указав Ф. И. О. и телефон; для предварительного решения — также паспортные данные |  |
| F6 | По заявке нового клиента с сайта система должна получить предварительное решение через скоринг и БКИ; затем отправить SMS с приглашением в отделение для идентификации и получения кредита | Новый клиент должен прийти в отделение для идентификации |
| F7 | В интернет-банке клиент должен видеть условия кредита и доступное ему предодобренное предложение, если оно есть | Предложение основано на ранее выполненном скоринге |
| F8 | При подаче заявки по предодобренному предложению система должна повторно проверить скоринг упрощённым способом, если данные могли измениться |  |
| F9 | Если клиент продолжит оформление заявки в отделении, сотрудник должен найти и продолжить уже существующую онлайн-заявку; для клиента без заявки — создать новую |  |
| F10 | Клиент должен получать SMS об изменении статуса кредитной заявки |  |
| U   | Удобство использования (Usability) |              |
| U1 | Интерфейсы сайта и интернет-банка должны быть удобны и интуитивны для пользователей |  |
| U2 | Интерфейсы должны следовать принятой в компании дизайн-системе и использовать привычные цвета и брендированные элементы |  |
| R   | Надёжность (Reliability)           |              |
| R1 | Интернет-банк (и новые сервисы) должны работать 24/7 и быть доступны в 99,9% случаев | Архитектурно значимое |
| R2 | Интернет-банк должен сохранять доступность при сбое основного ЦОД за счёт переключения на резервный ЦОД |  |
| P   | Производительность (Performance)   |              |
| P1 | Отклик операций должен быть максимально быстрым, порядка миллисекунд | Архитектурно значимое. Подразумевается внедрение мониторинга |
| P2 | Загрузка справочных данных, которая сейчас занимает больше секунды при платежах, должна стать быстрее |  |
| P3 | Кредитная заявка должна получить решение в течение одного рабочего дня, если данных достаточно; предодобренная заявка должна обрабатываться сотрудниками в тот же рабочий день | Архитектурно значимое |
| P4 | Интернет-банк должен поддерживать горизонтальное масштабирование и распределение запросов между серверами и ЦОД | Архитектурно значимое |
| S   | Поддерживаемость (Supportability)  |              |
| S1 | Для расширения интернет-банка следует избегать доработки его подрядного ядра, в том числе для SMS-функциональности | Архитектурно значимое |
| S2 | Для новых и изменённых компонентов необходимо подготовить документацию, чтобы их можно было расширять дальше |  |
| +R  | + Ограничения (Restrictions)       |              |
| +R1 | Трафик сайта и интернет-банка, содержащий чувствительные данные, должен быть зашифрован |  |
| +R2 | Доступ сотрудников депозитного и кредитного бэк-офисов к данным друг друга должен быть ограничен |  |
| +R3 | По возможности следует использоать технологии, уже имеющиеся в банке | Архитектурно значимое |
| +R4 | Не создавать дополнительную нагрузку на БД АБС и по возможности избегать прямых онлайн-вызовов интернет-банка к API АБС. | Архитектурно значимое |
| +R5 | Kafka рассматривается как предпочтительная очередь на перспективу, но её применение в текущем интернет-банке ограничено несовместимостью платформы. |  |
